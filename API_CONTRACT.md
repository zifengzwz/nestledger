# NestLedger API contract

API prefix `/api`. All responses JSON: success `{ "data": ... }`, failure `{ "error": { "code": "...", "message": "中文错误" } }`. Auth via HttpOnly SameSite=Lax cookie `nestledger_session`, session token cached in Redis (7 days), credentials included. JSON inputs. Object ids are strings, timestamps ISO8601 UTC. Money in integer cents (`amountCents`); input dates `occurredAt` ISO8601. Frontend Chinese language. Standard HTTP status codes.

## Auth
- POST /auth/sms/challenge `{phone,purpose:"register"|"phone_change"|"reset_password"}` -> `{challengeId,image,expiresIn:120}`; generates a local image challenge with letters and digits. Both SMS routes validate mainland China number format (`1[3-9]` followed by nine digits).
- POST /auth/sms/send `{phone,purpose:"register"|"phone_change"|"reset_password",challengeId,challengeCode}`; validates and consumes the challenge before calling the SMS provider. Successful response: -> `{retryAfter:60}`. `phone_change` requires a session. Codes are locally generated and verified, expire after 300 seconds, and are single-use. A phone can request one send per 60 seconds across purposes; at most five wrong guesses per code. Missing provider config returns 503; rate limits return 429. No standalone verification endpoint.
- POST /auth/register `{phone,password,name,smsCode}` -> user; automatically authenticated. Phone mainland China 11 digits starting 1; password 8-72 chars.
- POST /auth/login `{phone,password}` -> user
- POST /auth/password/reset `{phone,newPassword,smsCode}` -> `{ok:true}`. Requires a single-use `reset_password` code (template `100003`), bound to the account and credential version. Invalidates all existing sessions and does not log the caller in.
- POST /auth/logout -> `{ok:true}`
- GET /auth/me -> user or 401
- PATCH /auth/password `{currentPassword,newPassword}` -> `{ok:true}` (invalidate other sessions; preserve or rotate current)
- PATCH /auth/phone `{phone,currentPassword,smsCode}` -> user; verifies the current password and the new phone's SMS code.
- PATCH /auth/settings `{theme:"clay"|"forest"|"blue"|"plum"|"coral"|"mango"|"mint"|"berry"|"contrast-ink"|"contrast-navy"|"contrast-wine"}` -> user inside `{data:...}` (HTTP 200). Requires login; changes only this account's MongoDB `users.theme`. Invalid/missing theme, non-string or non-object JSON, or unknown fields return 400 `VALIDATION_ERROR`; non-JSON Content-Type returns 415, untrusted Origin returns 403, unauthenticated requests return 401. Theme persists across logout/login, is isolated between users, and does not change phone/password/authVersion or invalidate/rotate existing sessions.
User `{id,phone,name,createdAt,theme}`. `theme` defaults to `clay` for users without a saved field (no migration required), and is included in GET /auth/me and other user responses. Registration and phone changes require a local SMS code; password login and in-app invitations are unchanged.

## Books
- GET /books -> book[] accessible by current user, ordered by this account's saved `bookOrder`. Accessible books without a saved preference (including newly created/joined books) append in `createdAt` descending, then `id` descending order. Historical IDs for deleted/inaccessible books are ignored; users without a preference retain that default order.
- PATCH /books/order `{bookIds:[string]}` -> book[] in the requested order (HTTP 200, response `{data:[book]}`). Supply every currently accessible book ID exactly once; only the `bookIds` field is accepted and it must be a JSON array of valid 24-character lowercase hexadecimal IDs. Invalid/missing fields, non-arrays (including `{}`), malformed IDs or duplicates return 400 `VALIDATION_ERROR`; a still-existing but inaccessible book returns 403 `FORBIDDEN`; a missing/deleted ID or omitted/newly accessible book returns 409 `CONFLICT` with message `账本列表已变化，请刷新后重试` (refresh and retry). `[]` is accepted only if the account has no accessible books. Saves a BSON array at MongoDB `users.bookOrder`, not Redis or the book documents; preferences survive logout/login and do not change shared books or another member's order. Requires the same authenticated cookie, trusted Origin and application/json checks as other mutations.
- POST /books `{name,type:"personal"|"family"}` -> book
- PATCH /books/:id `{name}` -> book (owner)
- DELETE /books/:id -> `{ok:true}` (owner; delete records and invitations too)
- GET /books/:id/members -> `{ownerId,members:[user]}`
- DELETE /books/:id/members/:userId -> `{ok:true}` (owner can remove member; member may remove self; owner cannot leave)
Book `{id,name,type,ownerId,memberIds:[string],createdAt,readOnly:boolean,ownerName?:string,ownerPhone?:string}`. `readOnly` is true when the book was shared to the current account, which may then only view it; `ownerName`/`ownerPhone` identify the original owner to that recipient and are omitted for books the account owns or belongs to. Personal owner only (unless explicitly shared read-only); family owner/member. Invitations only owner.

## Invitations
- GET /invitations -> invitation[] pending to current phone
- POST /books/:id/invitations `{phone}` -> invitation (family owner only; phone must belong to an existing registered user). Unregistered phone returns HTTP 404 `{error:{code:"USER_NOT_REGISTERED",message:"该手机号尚未注册，请对方先注册后再邀请"}}` and does not create an invitation.
- POST /invitations/:id/accept -> book (phone matches)
- POST /invitations/:id/reject -> `{ok:true}`
Invitation `{id,bookId,bookName,inviterName,phone,status,createdAt}`. Prevent duplicate pending invites, owner/self/already-member invitations. Check identity again on accepting.

## Book sharing (read-only)
Sharing is an invitation: the book owner sends it to a registered phone, and the recipient must accept before gaining read-only access.
- POST /books/:id/shares `{phone}` -> share (HTTP 201 for a new invitation, 200 when re-sending a previously rejected one). Owner only. The phone must belong to an existing registered account; an unregistered phone returns 404 `USER_NOT_REGISTERED` and creates nothing. Sharing with yourself, sharing with a current owner/member, or sharing with a user whose invitation is still pending or already accepted returns 409 `CONFLICT`. Personal and family books can both be shared.
- GET /books/:id/shares -> `{ownerId,shares:[share]}` (owner only; includes pending, accepted and rejected rows).
- DELETE /books/:id/shares/:userId -> `{ok:true}` (owner only; 404 if that user is not currently shared). Pending or accepted access is removed immediately.
- GET /shares -> pending share invitations for the current account, newest first.
- POST /shares/:id/accept -> book (the recipient’s read-only book view, with `ownerName`/`ownerPhone`). Only the invited account may respond; a pending row is required.
- POST /shares/:id/reject -> `{ok:true}`. Only the invited account may respond; a pending row is required. The owner may send the invitation again afterwards.
Owner view share `{id,userId,name,phone,status:"pending"|"accepted"|"rejected",createdAt}`. Received share `{id,bookId,bookName,ownerName,ownerPhone,createdAt}`.
Only books whose share is accepted (or legacy share rows created before statuses existed) appear in the recipient's GET /books, with `readOnly:true` plus `ownerName`/`ownerPhone` so the recipient can tell whose ledger it is (the owner’s own view has `readOnly:false` and omits those fields). Pending and rejected shares grant no access at all. A read-only recipient may view records and analysis and may include the book in their own `PATCH /books/order`, but cannot create/edit/delete records, rename/delete the book, manage members or invitations, export, or import. Revoking the share or deleting the book removes access; deleting a book also deletes its shares, and accepting a family invitation removes any earlier read-only share for that user. Share relationships live in MongoDB collection `bookShares` (unique per book+user) and are not cached in Redis.

## Record options
- GET /record-options -> `{expenseCategories:[string],incomeCategories:[string],paymentSources:[string],expenseSubcategories:{"大分类":[string]},incomeSubcategories:{"大分类":[string]},customExpenseSubcategories:{"大分类":[string]},customIncomeSubcategories:{"大分类":[string]},icons:{expenseCategory:{"custom name":"icon-id"},incomeCategory:{...},paymentSource:{...}}}` inside `{data:...}`. Subcategory maps always contain every major category as a key (possibly `[]`) and list defaults followed by that account's custom subcategories. Requires login. The original three string arrays remain unchanged: defaults in the order below, then the current account's custom names in insertion order. Icon maps include custom options only, with `{}` (never `[]`) for kinds without custom options; legacy custom options without icon metadata fall back to `tag` / `coins` / `wallet` for expense / income / payment respectively.
- POST /record-options `{kind:"expenseCategory"|"incomeCategory"|"paymentSource",name:string,icon?:string}` -> the same complete options object including `icons`, HTTP 201. For a subcategory use `{kind:"expenseSubcategory"|"incomeSubcategory",parent:string,name:string}` instead: `parent` must be an existing major category of that kind, and `icon` is not accepted. Subcategories are unique within their parent (defaults included), allow at most 50 custom subcategories per major, and return the same complete options object with HTTP 201. Only these fields are accepted. Name is trimmed and must be valid UTF-8, 1–40 characters; invalid kind/name/icon, extra/missing required fields or non-object JSON return 400 `VALIDATION_ERROR`. `icon` must be an exact ID from the whitelist below; omitting it preserves existing clients and uses `tag` / `coins` / `wallet` according to kind (explicit null is invalid). A name already in that kind's defaults or custom names returns 409 `CONFLICT`; each kind allows at most 50 custom names (limit reached returns 409). Different kinds may contain the same name. Requires login, trusted Origin and application/json, like other mutations.
- POST /record-options/delete `{kind:"expenseCategory"|"incomeCategory"|"paymentSource",name}` or `{kind:"expenseSubcategory"|"incomeSubcategory",parent,name}` -> the same complete options object after deletion. Only custom options can be deleted; defaults return 409 `CONFLICT` and an unknown custom option returns 404. Deleting a custom major category also removes its custom subcategories and icon metadata. Deleting an option never changes historical records (they keep the stored category/subcategory/paymentSource strings), so export/import and analysis remain intact.
- Allowed icon IDs: `utensils`, `shopping-basket`, `bus-front`, `house`, `shopping-bag`, `gamepad`, `heart-pulse`, `graduation-cap`, `gift`, `circle-ellipsis`, `briefcase-business`, `award`, `chart`, `laptop`, `coins`, `message-circle`, `qr-code`, `credit-card`, `banknote`, `wallet`, `tag`, `paw-print`, `coffee`, `baby`, `smartphone`, `plane`, `bike`, `car`, `book-open`, `music`, `camera`, `sparkles`, `heart`, `shirt`, `wrench`.
- Defaults for expense categories: `['餐饮美食','日用百货','交通出行','住房物业','购物消费','休闲娱乐','医疗健康','教育学习','人情往来','其他支出']`.
- Defaults for income categories: `['工资薪酬','奖金收入','投资理财','兼职收入','礼金收入','其他收入']`.
- Defaults for payment sources: `['微信','支付宝','银行卡','现金','其他']`.
- Default subcategories (order preserved): 餐饮美食 `['早餐','午餐','晚餐','外卖','咖啡饮品','零食','水果']`; 日用百货 `['超市购物','清洁用品','厨房用品','纸品']`; 交通出行 `['公交','地铁','打车','加油','停车','火车/飞机']`; 住房物业 `['房租','房贷','水费','电费','燃气费','物业费','维修']`; 购物消费 `['服饰','数码','家居','美妆']`; 休闲娱乐 `['电影','游戏','旅行','运动','聚会']`; 医疗健康 `['门诊','药品','体检','牙科']`; 教育学习 `['学费','书籍','课程','培训']`; 人情往来 `['红包','礼品','请客','礼金']`; 其他支出 `['其他']`; 工资薪酬 `['基本工资','奖金','加班费','补贴']`; 奖金收入 `['年终奖','绩效奖','其他奖金']`; 投资理财 `['利息','分红','基金收益','股票收益']`; 兼职收入 `['兼职','稿费','副业']`; 礼金收入 `['红包','礼金','压岁钱']`; 其他收入 `['其他']`.
- Custom values remain account-private BSON arrays in MongoDB `users.customOptions.expenseCategories`, `users.customOptions.incomeCategories` and `users.customOptions.paymentSources`. Icon metadata is stored in matching BSON arrays at `users.customOptionIcons.expenseCategories`, `users.customOptionIcons.incomeCategories` and `users.customOptionIcons.paymentSources`, each item `{name,icon}`. Names (including `.` / `$` / `__proto__`) are string values, never MongoDB field keys; they become JSON map keys only on output. One atomic MongoDB update adds the name (`$addToSet`) and icon entry (`$push`) together, protected by the same uniqueness/capacity filters and `authVersion` guard, so losing duplicate/capacity races cannot write orphan icons or overwrite the winner. Both persist across logout/login and are not stored in Redis. Adding options/icons does not change historical records, shared books or other users' options/icons. Record endpoints continue accepting valid free-text category/paymentSource values, including historical names not in these lists.

## Records
UI labels call `paymentSource` / `paymentSources` “支付方式”. Internal API and MongoDB field names are retained for compatibility with existing records and saved custom options.
- GET /books/:id/records?from=ISO&to=ISO&type=income|expense&category=...&subcategory=...&q=...&createdBy=userId&page=1&pageSize=20 -> `{items:[record],total,page,pageSize,authors:[{id,name}]}` (from inclusive/to exclusive). `createdBy` filters to one recorder. `authors` lists current book members plus anyone who has recorded in the book, so the UI can offer a member filter even after a member leaves. List items also carry `createdByName` when the account still exists; create/patch responses keep the base record shape.
- POST /books/:id/records `{type,amountCents,category,occurredAt,note,paymentSource}` -> record
- PATCH /books/:id/records/:recordId same fields -> record
- DELETE /books/:id/records/:recordId -> `{ok:true}`
Record `{id,bookId,createdBy,type:"income"|"expense",amountCents,category,subcategory,occurredAt,note,paymentSource,createdAt,updatedAt}`; `subcategory` is `""` when not chosen. List responses additionally include `createdByName`. Members can view/create. Only creator or book owner edits/deletes. amount positive safe integer <= 99999999999 cents; note <=500 chars; category/subcategory/paymentSource <=40 chars. Date validated.

## Book export/import
- GET /books/:id/export?from=ISO&to=ISO -> `{format:"nestledger",version:1,exportedAt:ISO,book:{name,type},records:[{type,amountCents,category,subcategory,occurredAt,note,paymentSource}]}` in the ordinary `{data:...}` envelope. Owners and family members may export. Only `from` (inclusive) and `to` (exclusive) are accepted; invalid/inverted dates or unknown query parameters return 400. Stable `occurredAt ASC,id ASC`; at most 5000 records, otherwise 422 `EXPORT_LIMIT_EXCEEDED` with a request to narrow the date range. Empty records encode `[]`. No record IDs, creator/member IDs, account settings or other private user data are exported.
- POST /books/:id/import `{requestId:string,records:[same fields; subcategory optional for legacy],dryRun?:boolean}` -> `{validated:true,count,dryRun:true}` on dry run (200), or `{importedCount,replayed,requestId}` on commit (201 fresh, 200 replay), wrapped in `{data:...}`. Owners and family members with current access may append; imported `createdBy` is always the current account. Existing records are never overwritten. Cookie/Origin/application-json checks apply; import authentication and book access are checked before reading or decoding its larger body.
- `requestId` must be 16–64 ASCII letters/digits/hyphens. `records` must be a genuine JSON array with 1–5000 rows. Strict top-level/row field whitelists and ordinary record validation apply to every row before any write; a bad row returns 400 with its 1-based row number. `dryRun` is optional boolean, validates only, and does not write records or receipts. Dates/category/payment source are normalized by the existing record validator. Import alone accepts up to 10MiB JSON; all ordinary API bodies remain limited to 16KiB (413 `BODY_TOO_LARGE`).
- MongoDB `importReceipts` is uniquely scoped by current user + target book + requestId. SHA256 fingerprints hash arrays of normalized fixed-order tuples `[type,amountCents,category,subcategory,occurredAt,note,paymentSource]`, including row order, never Lua object-key iteration. Same token/same normalized content replays safely; different content with an existing token returns 409 `IMPORT_CONFLICT`, including after completion. Concurrent processing/recovery returns 409 `IMPORT_IN_PROGRESS`. Receipts are not stored in Redis.
- Generated records have an internal `importBatchId`; writes use ordered BSON batches of at most 100 records. On a known write failure, best-effort rollback deletes only that account/book/batch, leaving ordinary and older records intact. A durable `retryable` or `rollback_pending` receipt allows the same requestId/content to recover cleanup and retry without duplication. An unresolved rollback returns 503 `IMPORT_RECOVERY_REQUIRED`: retain the same requestId rather than creating another token.
- Standalone MongoDB has no cross-collection transaction; concurrent readers may observe a partial in-progress batch. A hard worker crash or unresolved final commit acknowledgement can leave a `processing` receipt; the API deliberately returns `IMPORT_IN_PROGRESS` rather than stealing an expiring lease. Operators must first establish the old execution has stopped, then inspect the scoped receipt and batch: verify a fully completed batch and access checks before marking `committed`, or mark `rollback_pending` to let the same request clean up/retry. Never blindly delete a completed batch or reset its token. If final acknowledgement is lost but a committed receipt can be re-read, success/replay is returned and that batch is not rolled back. Unresolved dependency failures are explicit, not claimed as successful imports.

## Analysis
- GET /books/:id/analysis?period=week|month|year&date=YYYY-MM-DD&member=userId -> `{period,from,to,incomeCents,expenseCents,balanceCents,recordCount,trend:[{label,incomeCents,expenseCents}],categories:[{category,amountCents,count,subcategories:[{name,amountCents,count}]}],members:[{userId,name,incomeCents,expenseCents,balanceCents,recordCount}]}`. `member` restricts the top-level totals/trend/category ranking to one recorder; `members` always reports the whole selected period for every current member (including zero-record members) plus historical recorders, so the UI can show a per-member breakdown and switch filters. `member` must be a valid object id; invalid ids return 400.
Period calendar in Asia/Shanghai: week Monday through Sunday, month, year. Trend week/month daily and year monthly; categories expense descending. date defaults current Shanghai day. Zero buckets included.

- GET /analysis?period=week|month|year&date=YYYY-MM-DD -> account-wide analysis across books the current account owns or belongs to, counting only records whose `createdBy` is the current account. Read-only shared books are excluded. Response has the same totals/trend/category shape plus `books:[{bookId,name,incomeCents,expenseCents,balanceCents,recordCount}]` and `members:[]`; `books` includes owned/member books even when they have no records in the period. Invalid period/date returns 400.

## Misc
- GET /health -> `{status:"ok",mongo: true,redis:true}` or 503 dependency health.

Runtime: Vue Vite built and served by locally installed OpenResty, `/api` Lua router; locally installed MongoDB (5+, recommended 7) and Redis7 bound to loopback. Direct MongoDB OP_MSG+BSON Lua driver on the trusted host (never expose db ports publicly); no Python/Node replacement backend. No container deployment. Tests may run with stubbed ngx sockets or actual services.
